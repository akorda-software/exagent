## Hallazgos, autorización y cambios acotados

1. **Default ignorado:** el adapter aceptaba HTTP receive_timeout por instancia
   pero lo sustituía por60000. Ahora precede settings.timeout no nil, luego
   instancia, luego60000; se traduce una vez, no también en req_http_options.
2. **Instrucciones duplicadas/reinsertadas:** params.instructions se prefijaba a
   historia que ya contenía System. El adapter ahora respeta sólo mensajes
   canónicos/proyectados seleccionados por core/hooks, igual que legacy. Caso
   discriminante con System proyectado distinto de metadata de definición.
3. **Incompatibilidad real del lock:** ReqLLM1.24 genera Finch keyword options;
   Req0.6.1 las pasaba como nombre a Registry.lookup, fallando antes de conectar.
   Los transportes-función anteriores no ejercían esta frontera. El coordinador
   autorizó Req0.7.4 + floor `~>0.7.4`; la resolución movió también Finch a0.23,
   pero se restauró **sólo** su entrada0.22 original con autorización y deps.get
   la conservó. Cambio final respecto al inicio: **sólo Req**; Mint1.10.1/HPAX y
   restantes versiones sin cambio. Req0.7 soporta `finch: options` desde0.7.0;
   se exige el patch concreto0.7.4 validado, no se inventa que introdujo esa API.
4. **Total por instancia:** tras demostrar API pública y necesidad real, el
   coordinador autorizó `Adapter.total_timeout`: positivo en ms o nil (default
   upstream, normalmente infinity). Traduce sólo al keyword público ReqLLM;
   no cambia ModelSettings ni confunde receive, pool y deadline de todo el run.
   Timeout total devuelve RequestError saneado `{:timeout, :total}`; run conserva
   su wrapper `{:model_request_failed, error}`. Sin garantía de rollback ni de
   cancelar descendientes arbitrarios de callbacks host.

ADRs8.19–8.21 y migración documentan problema/beneficio/alternativas/impacto/tests.
Se rechazó mantener root roto, añadir shim de Finch o parchear privados. El cambio
Req no repara ninguno de los gaps stock1.24. No hubo bump ExAgent, fork, publicación,
config global del host, instalación de tooling ni llamadas LLM/DB/backend reales.

### Timeouts: observación delimitada

- Receive40ms con peer reteniendo headers falla (≈62–70ms incluyendo preparación).
- Stock total50ms frente a receive500ms corta HTTP trickle≈51ms.
- Callback deliberadamente bloqueada: total300ms termina su Task propia≈301ms;
  DOWN observado y callback no completa. No prueba cancelación de código/efectos
  fuera de esa Task. El primer supuesto de probe era incorrecto y se conserva rojo.
- Pool30ms bajo ocupación rechaza **antes de segunda conexión**, mediante una
  RuntimeError pública de exceso de cola; no devuelve el tuple asumido al principio.
- Adapter por Model/run con total100ms y receive1000ms: una petición TCP aceptada,
  socket cerrado, error total saneado, request_count1 y usage partial/cost unknown.
  La operación ReqLLM no incluye toda preparación/ejecución del agente.

## Escenario compuesto R1.7 textual (sin fix del runtime necesario)

`test/exagent/req_llm_text_runtime_test.exs` usa ReqLLM real con **adapter sintético**,
no TCP ni backend real. No confundirlo con el loopback de timeout_test.

- Server→modelo→Store ETS, primer save falla; se preserva resultado/unknown,
  admisión posterior bloqueada, checkpoint retry sólo guarda sin regenerar.
- Session aplica el resultado en función de transición pura, fuera de efectos
  modelo; coordina y persiste su estado/roster. Restore de Server+Session conserva
  historia y estado, vuelve a asociar el ref vivo proporcionado por el host.
- Hook before/after una vez por request; compaction local afecta sólo proyección,
  mantiene System una sola vez y no reescribe historia/checkpoint canónicos.
- Scope con request_limit1 por run; tres requests Req mediante transporte
  sintético = tres generaciones telemetry = tres spans model/chat y tres spans run.
  No doble span ni ID duplicado; coste unknown y tokens GenAI no inventados.
- Response.usage nil sobrevive JSON/snapshot; los contadores agregados persistidos
  son subtotales, no se presenta esta prueba como ledger de disponibilidad de uso
  global/duradero. Key sintética ausente de snapshot/spans.

OTel es un provider/processor de test con exporter en memoria, SDK root ya existente;
no backend Opik, SQL ni obligación SDK en consumidor mínimo. No se ejercitan
delegación/tool/stream bloqueados para inflar paridad.

## Decisión siguiente y alcance restante

Matriz única de estado/gaps y alternativas en roadmap §5. El siguiente paso para
cerrar R1 es una decisión explícita de dependencia pública con fidelidad de
argumentos, bloques/firmas, presupuestos byte y uso observado; no otra expansión
independiente ni R2. Preferencia: release upstream con APIs públicas y gates de
frontera. Alternativa sólo si se autoriza: extensión/patch pequeño versionado,
revisado, con procedencia y retirada al publicarse upstream; nada se adopta aquí.
El spike usage aislado no resuelve por sí solo args, redacted o bytes.

R1.6 parcial: tramo textual disponible; negociación/tool_choice/output, retry
contable/uso y streaming dependen de gaps. R1.7 parcial: escenario textual, no
paridad tools/delegación/stream/metadata completa. R1.8 no retira legacy. Los guards,
unknown y unsupported siguen activos; no se rebaja el alcance v2 para declararlo listo.
