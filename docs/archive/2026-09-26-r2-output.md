## Refusal: límite demostrado y decisión explícita

Stock Chat1.24 descarta `message.refusal` buffered y `delta.refusal` stream junto a
content válido. Gate compara control `{}` sin refusal vs mismo contenido+refusal:
`Response.refusals/1`, message.content/metadata, provider_meta, finish_reason,
object y output_items son iguales. En stream el JSON aparece como objeto público;
buffered como texto. Por tanto puede producir output localmente válido aun con una
señal wire perdida; no anunciar detección total. No es JSON inválido reparado.

Coordinador respondió al ask continuar con semántica pública documentada bajo8.22/
8.26, mantener negativos y exigir revisión fresca de esta formulación. El adapter
rechaza `Response.refusals(response) != []` antes de cualquier sibling effect.
Como Chat no retiene ese campo, el oráculo **host** usa un response-step público
Req que añade provider_meta.refusal al Response ya decodificado por stock. Comprueba
guard y efecto0; **no demuestra fidelidad wire** y no sustituye el gate TCP real.
Refusal habitual sin contenido válido se prueba por wire stock y falla. No se
calificaron familias con metadata de continuación perdida.
